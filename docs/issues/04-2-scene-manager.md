# [단계 4-2] SceneManager와 장면 바꾸기

## 목표와 범위

장면(Scene)을 하나 더 두고 바꿀 수 있게 한다. 타이틀 장면에서 키를 누르면 전투 장면으로 넘어간다. 장면의 주인은 새로 만드는 SceneManager다. Application은 SceneManager를 갖고, SceneManager가 지금 장면을 갖는다. 장면은 파일이 아니라 장면마다 채우는 코드다(타이틀용, 전투용). 바꾸기 요청은 기록만 하고, 정한 시점에 옛 장면을 지우고 새 장면을 만든다. 선행: 단계 4-1.

2026-11-09 학생 결정: "필요해 타이틀도 있고 화면 전환도 있기때문에 무조건 있게 설계하자", "4-2 전에 먼저", "4-2로, 재생은 4-3". 처음 설계의 "Scene 하나면 충분하다"를 학생이 바꾼 것이다. 재생(Animator)은 4-3(이슈 #17)으로 간다.

- 포함: SceneManager(지금 장면 소유, 바꾸기 요청과 반영, 지금 장면의 카메라), 장면 번호(SceneId), 장면별 채우기 함수(타이틀·전투·데모), 타이틀에서 키로 전투 진입, 바꾸는 시점 규칙, CPU 시험, 창 모드 확인.
- 제외: 타이틀 글자·로고(2D 그리기, 로드맵에 없음. 첫 타이틀은 3D 물체와 카메라만), 장면 파일·에디터, 전환 효과(페이드), 여러 장면 동시 유지, 재생(4-3).

## 모듈 계약

- **SceneManager**: Application이 소유한다. `std::unique_ptr<Scene>`로 지금 장면 하나를 갖고, 지금 장면의 카메라 주소를 기억한다. `RequestChange(SceneId)`는 요청을 기록만 한다. Application이 정한 시점에 반영 함수를 부르면 옛 장면을 지우고(소멸자) 새 Scene을 만들어 채운다. 원본(AssetManager의 모델, 바닥 메시)은 장면보다 오래 살고 Renderer의 GPU 버퍼 캐시도 그대로다.
- **장면 채우기**: Application의 함수다. 지금 `BuildWindowScene`이 전투 장면의 시작이고, 타이틀 장면과 데모 장면이 더해진다. 데모 출력은 4-1과 같아야 한다.
- **호출 시점**: 요청은 tick 안·Update 안 어디서 해도 되고, 반영은 한 곳에서만 한다. 어디인지(프레임 끝 / 다음 프레임 시작)는 설계 문서에서 학생이 고른다.
- **창구 규칙**: 컴포넌트가 요청을 부를 수 있게 하면 Scene이 알려 주는 서비스가 Input·Time·SceneManager 셋이 된다. 그렇게 할지도 학생이 고른다.
- **오류**: 장면을 바꾸는 도중(옛 장면 소멸자 안)의 요청은 금지한다. 4-1의 "소멸자에서 CreateObject·Clear 금지"와 같은 규칙이다.

정할 것(4-2 설계 문서에서 학생이 고른다): 바꾸기 요청을 누가 부르나(컴포넌트 / Application), 언제 바꾸나(프레임 끝 / 다음 프레임 시작), 같은 장면을 다시 요청하면(다시 만든다=재시작 / 무시), 한 프레임에 두 번 요청하면(마지막 것 / 첫 것 / 오류).

## 완료 조건

- [ ] 창 모드가 타이틀 장면으로 시작하고, 정한 키를 누르면 전투 장면(4-1의 Player·Kraken·바닥·카메라)으로 바뀐다.
- [ ] 바꾸기 요청만으로는 장면이 바뀌지 않고, 정한 시점에 한 번에 바뀐다. tick 안에서 요청해도 그 tick은 끝까지 돈다.
- [ ] 장면을 바꿀 때 옛 장면의 객체·컴포넌트가 지워지고, 모델 원본은 다시 읽지 않는다(`Load model` 로그 1번).
- [ ] 데모 출력이 4-1과 같다.
- [ ] 설계 검증 보고서(4-2 전환)의 반드시 정할 것이 단계 문서에 적혀 있다.

## 학생 질문과 과제

1. SceneManager가 장면을 바꾸면 사라지는 것과 남는 것은 무엇인가(객체·컴포넌트·모델 원본·GPU 버퍼)?
2. 바꾸기 요청을 그 자리에서 바로 반영하면 어떤 문제가 생기는가? 왜 한 곳에서만 반영하는가?
3. 단계 6의 재시작을 이 SceneManager로 하려면 어느 함수를 어디서 부르면 되는가?

변형 과제: 전투 장면에서 키 하나로 타이틀로 돌아가게 하고, 돌아갈 때마다 `Load model` 로그가 몇 번 찍히는지 확인해 이유를 설명한다.
